# 工作台更新器完善计划（对标 SUG standalone 更新器）

> 2026-07-11 起草，基于 main（release 3.1.7.4）与 SUG submodule（SUGv1.3.7）对比。
> 目标：让 Karaoke Studio 工作台的自动更新体验达到 SUG standalone 模式的完成度。

> 2026-07-13 校准：工作台已接入 SUG 的 PyQt6 更新器界面，`Updater.exe`
> 改为 onefile + windowed 构建；正常更新不再弹出控制台。下文关于“当前 console”
> 和“GUI updater 仅作预留”的内容属于实施前历史对比。

## 一、SUG 更新器机制总结

SUG 的更新器分四层，全部在 submodule 内（`src/strange_uta_game/updater/` +
仓库根 `updater_app/` + `scripts/release.py`），文档见 SUG `docs/auto_update.md`。

### 1. 检查层（主程序内，`updater/` 包）

| 模块 | 职责 |
|---|---|
| `settings.py` | `config.json → updater` 节点：总开关、启动检查、8h 防抖、源排序、代理、跳过版本 |
| `sources.py` | 三个下载/API 源（github / ghproxy / fastgit），用户可拖拽排序，失败逐源接力 |
| `proxy.py` | 四种代理模式：关闭 / 系统代理（读注册表）/ 自动检测（扫描 18 个常见本地端口）/ 手动指定 |
| `version.py` | 无依赖 SemVer 解析：`X.Y.Z[-suffix]`，正式版 > 预发布，tag 前缀剥离 |
| `http_client.py` | `get_json` / `get_text` / `download`（**断点续传 + 3 次重试 + 进度/取消回调**）+ `SourceTrialRunner` 多源接力 |
| `manifest.py` | 拉取 latest release；**302 跳转兜底**（API 全 403 限流时用 `github.com/…/releases/latest` 的重定向探测版本号，不吃 API 配额）；**`fetch_releases_since` 跨版本 changelog 聚合**（1.0.0→1.0.3 时弹窗展示 1.0.1/1.0.2/1.0.3 全部日志）；镜像源资产 URL 改写 |
| `worker.py` | QThread 异步检查；**403 限流专属错误文案**（区分"机场共享 IP 撞 API 配额"和"网络不通"） |

### 2. UI 层（`updater/ui/`）

- `update_dialog.py`：更新弹窗，渲染 Release body（Markdown），聚合展示所有中间版本日志；三个按钮（立即更新 / 稍后再说 / 跳过此版本）。
- `update_card.py` + `source_order_dialog.py` + `proxy_card.py`：设置页卡片（开关、防抖小时数、源排序拖拽弹窗、代理配置 + 连通性测试）。
- `update_progress_window.py`：**点"立即更新"后、主程序退出前**的无边框进度窗（进度环 + 可取消），覆盖"自更新 Updater.exe"的下载阶段。

### 3. 交接层（`installer.py`，670 行）

- 定位 Updater（优先 onedir 的 `UpdaterEx.exe`，回退 onefile `Updater.exe`），复制到 `%TEMP%` 防自锁（onedir 需为 `_internal` 建 junction）。
- **Updater.exe 自更新**（解决鸡生蛋）：启动 Updater 前，先拉远端 manifest 对比 `parts.app.sha256` 与本地 `_internal/.installed_manifest.json`；不一致才下载 app part zip，提取新 Updater.exe 替换本地（字节级双保险）。下载的 part zip 保留在 `%TEMP%/…/parts/`，Updater 增量更新时直接复用，不二次下载。
- 读 PE 头 Subsystem 决定启动方式：GUI updater 用 `DETACHED_PROCESS` 不弹控制台，console updater 用 `CREATE_NEW_CONSOLE`。
- 传 `--pid` / `--url source|url`（可重复，按用户源排序）/ `--proxy` / `--sha256` / `--locale`。

### 4. 独立 Updater（`updater_app/main.py`，1369 行）

等待主进程 PID 退出（30s 超时强行继续）→ 两条路径：

- **增量路径 `run_incremental`**：按 asset 名派生 manifest 文件名（`StrangeUtaGame-…-v1.0.3.zip → manifest-…-v1.0.3.json`），逐源拉取；与本地 `.installed_manifest.json` diff 出变化的 part（`app` = EXE+Updater+应用代码包，`runtime` = 其余 `_internal`）；只下载变化 part（内容哈希校验，本地已有且哈希一致则**零下载复用**）；逐 part 备份→替换→失败回滚；写回本地清单。
- **全量兜底 `run`**：manifest 拉不到 / schema 不支持时回退——下载全量 zip（断点续传、跨源切换时清残留防数据混合）、`.sha256` 校验、备份 `_internal.bak` + `.exe.bak`、替换、失败回滚、重启主程序、清理。
- 严格只动 EXE 与 `_internal/`，**绝不碰用户数据**；日志在 `%TEMP%/StrangeUtaGameUpdater/updater.log`；失败退出码分级（下载失败 3 / 校验失败 4 …）。

### 5. 发布工具链

- `scripts/release.py prepare X.Y.Z`：注入 `__version__.py` + CHANGELOG 占位段。
- `scripts/release.py build`：构建全量 zip + **app/runtime part zip + manifest json + 各 `.sha256`** + 出厂 `.installed_manifest.json`（烤进 `_internal/`），从 CHANGELOG 抽 release notes；支持 main / noWinIME / mac 三变体。
- GitHub Actions：push `SUGv*` tag 全自动构建发布。
- 单元测试 8 个文件 73+ 项（version / sources / proxy / manifest / settings / installer / updater_main / release_script）。

## 二、KS 现状与差距

KS 在 3.1.x 已移植了 SUG 更新器的**骨架**，且 `Updater.exe` 直接复用 SUG 的
`updater_app`（[krok_helper/updater_app/main.py](../krok_helper/updater_app/main.py)
仅覆写 `TMP_DIR_NAME` / `PRODUCT_NAME` / UA），所以**增量更新、断点续传、备份回滚、
sha256 校验的代码已经随 Updater.exe 分发给所有用户**——只是构建端从不产出
manifest/parts，增量路径永远走不到。

### 已对齐 ✅

- 设置节点（同 schema）、8h 防抖、跳过版本、启动/手动检查
- 源排序（4 个镜像，比 SUG 还多一个）、代理四模式（`krok_helper/network.py`）
- 设置页更新卡片、`WorkbenchUpdateDialog` 更新弹窗（展示 Release body）
- 手动检查失败时逐源错误明细
- Updater.exe：等待 PID、多源接力、sha256、备份回滚、重启（复用 SUG 全套）
- CI：tag `v*` 自动打包发布，zip + `.sha256` 资产

### 差距 ❌

| # | SUG 能力 | KS 现状 | 影响 |
|---|---|---|---|
| 1 | 302 跳转兜底 + 403 专属文案 | 无 | 机场共享 IP 撞 GitHub API 限流时直接报"无法访问任何更新源"，误导用户查网络 |
| 2 | 跨版本 changelog 聚合 | 只显示 latest body | 跳版本升级的用户看不到中间版本改了什么 |
| 3 | manifest + parts 增量更新 | Updater 代码支持，但构建不产 manifest/parts/出厂清单 | 每次更新全量下载整个 zip（几百 MB），日常 bugfix 实际只变几 MB 应用代码 |
| 4 | installer 侧 Updater.exe 自更新（启动更新器**之前**先换新） | 无（[installer.py](../krok_helper/updater/installer.py) 131 行，缺整段自更新逻辑）。注意旧客户端并非无法更新更新器——见下方「更新器自身的升级通道」 | 更新器修复滞后一代；若旧更新器的 bug 恰好导致更新本身失败，则形成死锁，只能手动下载 |
| 5 | 更新准备进度窗（可取消） | 点"立即更新"直接退出主程序 | 自更新 Updater 落地后必需，否则下载期间界面假死无反馈 |
| 6 | PE Subsystem 检测 / onedir UpdaterEx | 固定 console + onefile | 暂可接受，为将来 GUI updater 预留 |
| 7 | 主程序侧 `http_client`（续传/重试/接力） | 主程序侧无下载能力 | #4 的前置 |
| 8 | `release.py prepare/build` 一键发版 | 手动流程（docs/release-process.md） | README 版本号常漏改（AGENTS.md 已知坑 #7）、中文 release body 靠手动 `gh release edit`（坑 #5） |
| 9 | 更新器单元测试 73+ 项 | 2 个测试文件 | 回归保障弱 |
| 10 | `docs/auto_update.md` 完整文档 | AGENTS.md §5 五行简介 | 维护/接手成本 |

### 命名适配的两个坑（增量更新的关键）

1. **manifest 文件名派生是硬编码的**：SUG `try_fetch_manifest` 用
   `asset_name.replace("StrangeUtaGame", "manifest", 1).replace(".zip", ".json")`。
   KS 资产名 `KaraokeStudio-windows.zip` 中没有 `StrangeUtaGame`，派生结果是
   **`KaraokeStudio-windows.json`**。两个选项：
   - **a（短期可行）**：接受该名字，KS 构建端就上传 `KaraokeStudio-windows.json`；
   - **b（推荐，走 SUG PR）**：把前缀参数化为模块级常量（如 `MANIFEST_PREFIX`，
     与 `PRODUCT_NAME` 同款覆写机制），KS 包装层覆写后用 `manifest-windows.json`
     这类正常名字。旧版 KS 客户端已按 a 规则派生，**上传资产时两个名字都传**可兼容。
2. **installer 自更新的 app part 名派生**：SUG 用
   `asset_name.replace(f"-v{version}.zip", f"-v{version}-app.zip")`，KS 资产名
   不带版本号，replace 落空会拼出错误 URL。KS 移植版**不做字符串派生，直接读
   manifest `parts.app.asset`**（Updater 侧 `_download_part` 本来就是这么做的）。

另外注意：**一旦开始上传 manifest，存量旧客户端的 Updater.exe 也会立刻走增量路径**
（它们已带该代码）。旧客户端本地无 `.installed_manifest.json` → diff 视为全部 part
变化 → 下载 app+runtime 两个 part（≈全量体积）并写入本地清单，之后的更新才享受增量。
上线前需在本地用旧版 Updater.exe 实测这条"首次增量"路径。

### 更新器自身的升级通道（2026-07-11 已核实）

「旧版本不持有新更新器」不构成问题，因为**更新器随主程序更新包一起分发**：

- KS 构建把 `Updater.exe` 放在 zip 根目录（`build_windows.bat` 第 222-226 行，
  必备文件校验含 `Updater.exe`）。
- 旧 Updater 的全量路径 `apply_update`（SUG `updater_app/main.py` 第 683-699 行）
  在替换主程序的同时，会把 app 目录里的 `Updater.exe` rename 成 `.old` 并复制
  zip 里的新版进去（自己跑在 %TEMP% 副本上，不锁 app 目录本体；`.old` 由下次
  启动的 `_cleanup_old_files` 清理）。**该逻辑从 KS 最早带更新器的 v3.0.1 pin
  起就存在**（引入 commit `5e213e3` 是所有 KS pin 的祖先）。
- 增量路径同理：manifest 的 app part `targets` 明确包含 Updater.exe。

因此这是一个**滞后一代模型**：执行第 N 次更新的永远是 N-1 代更新器，更新完成后
用户才持有 N 代。它的唯一软肋：若 N-1 代更新器的 bug 恰好使"这一次更新"失败，
用户会死锁在旧版（拿到修好的更新器需要先成功更新一次）。Phase 3 的 installer 侧
自更新就是把顺序反过来——主程序在**启动更新器之前**先从远端 app part 提取新
Updater.exe 替换本地，再启动新更新器干活，让更新器 bug 的修复不依赖旧更新器
自己成功跑一遍。注意它保护的是 Phase 3 落地**之后**的客户端；对存量客户端的
当次更新无追溯力（它们的主程序里没有这段代码），存量客户端的兜底仍是
「全部源失败 → Updater 退出码 3 + 控制台提示 → 引导 GitHub 手动下载」。

### 跨版本升级兼容性（2026-07-11 已按 git 历史核实）

存量用户版本分布对更新器的意义：

| 用户版本 | 随包 Updater | 跨版本直升行为 |
|---|---|---|
| v2.x / v3.0.0 | **无更新器** | 自动更新完全不可达，只能 README/发布页引导手动下载 |
| v3.0.1 – 当前 | 全部带增量代码，`SUPPORTED_MANIFEST_SCHEMA = 1`（逐 tag 的 submodule pin 已核实） | 见下 |

跨版本直升（如 3.0.1 → 3.2.0）之所以天然安全，依据是：

1. **parts 是内容快照不是补丁链**。manifest 的 app/runtime part 都是完整内容 zip，
   按 sha256 寻址，不存在"必须先装 3.1.x 再装 3.2.x"的顺序依赖。任意旧版一步
   到位，装完写入本地清单即与最新版对齐。
2. **每一层失败都降级为全量**，永不砖机：manifest 拉不到（含命名对不上）→ 全量
   zip；`schema > 1` → 全量 zip；part 哈希校验失败 → 全量 zip；全量替换失败 →
   回滚备份。所以命名方案 b（`manifest-windows.json`）对旧客户端的最坏后果只是
   "第一跳没有增量"，若想让旧客户端第一跳也吃到增量，把派生名
   `KaraokeStudio-windows.json` 一并上传即可（两个名字指向同一内容）。
3. **manifest schema 字段就是为将来断代准备的**：以后若 part 结构要大改，发
   schema 2 的 manifest，所有旧 Updater 自动回退全量，新 Updater 走新逻辑。

由此得出几条**发布不变量**（写入 release-process.md，违反任何一条都会甩掉旧客户端）：

- `KaraokeStudio-windows.zip` / `-macos.zip` + `.sha256` 必须**永远随 release 上传**
  （旧 worker 硬编码此名，全量兜底也靠它）；增量资产只做增补，不做替换。
- 主程序 EXE 名 `Karaoke Studio.exe`、onedir「EXE + `_internal/`」布局不可改名/改结构
  ——旧 Updater 用旧 app 传入的 `--app-exe` 替换后重启，改名会导致重启失败。
- tag 保持 `vX.Y.Z[.N]`；旧版 `_version_key` 对 4 段号比较正确（已验证
  `(3,2,0) > (3,1,7,4)` 语义成立），不要引入其他 tag 花样。
- 不 force-push 已发布 tag（AGENTS.md 坑 #6，跨版本场景下危害翻倍：旧客户端
  缓存的 part 哈希会与重打的资产对不上，全部退化全量）。

跨版本的**信息面**问题：旧客户端弹窗只显示 latest release body（没有 Phase 1 的
聚合能力），所以每个 release body 开头应自带「从旧版本升级？完整变更见 CHANGELOG」
链接；Phase 1 的 `fetch_releases_since` 注意 GitHub list API 默认 30 条/页，
跨很多版本时要 `per_page=100` 或翻页。配置层面跨版本无忧：`UpdaterSettings.load`
以 DEFAULTS 合并缺失字段，旧 `config.json` 直接可用（其他设置模块同理，属应用侧
通用职责，不在本计划范围）。

### 与 SUG 方案的偏差清单

本计划的机制、流程、失败矩阵**严格照搬 SUG**（Updater.exe 更是直接复用 SUG 代码），
仅以下几处因 KS 语境不同而**有意偏离**，除此之外不做发挥：

| # | 偏差 | 原因 |
|---|---|---|
| 1 | 版本比较保留 KS 的 4 段 `_version_key`，不采用 SUG `version.py` | **强制偏差**：SUG 正则把 `3.1.7.4` 的第 4 段解析为 pre-release 后缀，会得出 `3.1.7.4 < 3.1.7` 的错误结论，直接照搬会让流程 B（第 4 段递增）的发版判断反向 |
| 2 | manifest/part 命名不用字符串派生，installer 自更新直接读 manifest `parts.app.asset` | SUG 的 `replace("StrangeUtaGame",…)` / `replace("-v{ver}.zip",…)` 派生规则对 KS 的无版本号资产名不成立（详见上文命名坑） |
| 3 | 不引入 SUG 的变体体系（main/noWinIME/mac 三套资产） | KS 只有 windows/macos 两个平台资产，macOS 无 Updater，维持全量+手动 |
| 4 | 不传 `--locale` | KS 中文单语言 |
| 5 | Updater 保持 onefile console，不构建 onedir `UpdaterEx.exe` / GUI updater | KS `build_updater.py` 显式 exclude PyQt6/qfluentwidgets 控制体积（~12MB）；PE Subsystem 检测仅作预留 |
| 6 | `release.py` 围绕 KS 现有 `build_windows.bat` + workflow 组织，不照搬 SUG `build.py` 结构 | KS 已有自己的构建脚本与 CI 资产约定（AGENTS.md 坑 #2） |
| 7 | 镜像源保留 KS 现有 4 源（github/ghproxy/gh-proxy/ghproxy-net） | 比 SUG 文档的 3 源（含已不可用的 fastgit）更新 |
| 8 | runtime 复用指纹随 release 资产走（manifest `build` 字段 + CI 拉上一版资产），不用 SUG 的 git 提交缓存（`.runtime-hash-cache.json` + `runtime-latest.zip`） | KS 发版只在 CI 跑，CI 无法把缓存文件 commit 回仓库；SUG 是本地构建为主 |
